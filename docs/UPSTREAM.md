# Upstream findings

Engine behaviors discovered while building blitz-py. First found against `blitz 0.3.0-beta.1` / `fontique 0.10` / `vello_cpu 0.0.9`; last re-checked 2026-11-17 against blitz-py's Blitz (`adrienbrault/blitz` branch `blitz-py` @ `d9099efa`: upstream main @ `81b4896` + outline-offset + text-overflow ellipsis) / `parley`+`fontique 0.13` / `stylo 0.24` / `anyrender 0.15` / `anyrender_vello_cpu 0.19` (vello_cpu 0.4). Kept here as the source of truth for our workarounds; revisit on every dependency bump.

| Finding | Where | Our workaround | Status upstream |
|---|---|---|---|
| `parley::FontContext::new()` leaks ~115KB per call (platform font scan) and costs ~25ms | fontique 0.10, still present in 0.12 (re-measured with `examples/leak.rs`) | Build the font collection once, clone per render (`base_collection()`) | Not reported (repro: `examples/leak.rs`, stages `fontctx` vs `paint`) |
| Without a `base_url`, the document base is a `data:` URL, which cannot anchor relative URLs; `resolve_url` then panics on `<img src="logo.png">`, `<link href="a.css">`, `<iframe src>`, `//host/x` | blitz-dom `DocumentUrl::default` + `BaseDocument::resolve_url` (`unwrap_or_else(panic!)`), beta.1 through beta.4 | Default to the hierarchical base `blitz-py:///`; reject non-hierarchical `base_url`s with `ValueError` | Not reported |
| Images are decoded in full with no pixel limit (`ImageReader::decode()` with the image crate's default 512MB allocation cap), so a few-KB PNG declaring 9000x9000 allocates ~400MB | blitz-dom `ImageHandler::parse`, beta.4 | `SyncProvider` sniffs the header and drops images over `MAX_PIXELS` | Not reported |
| Stylo leaks a per-thread bloom filter and style-sharing cache: `Box::leak` into TLS (`bloom.rs`, `sharing/mod.rs`, "we don't have the guarantee of TLS destructors to run in worker threads"), so every *new* thread that styles a document costs ~37KB forever (`examples/leak.rs` stage `thread_doc` vs `thread_noop`/`doc_shared`) | stylo 0.22 via blitz-dom beta.4 (not re-measured on stylo 0.24) | Render on reused pooled threads (`with_render_stack`); a `Template` keeps one worker | By design upstream; spawning a thread per render was our bug (geekmagic-hacs#209, fixed in 0.6.0) |
| SVG `<text>` resolves fonts via usvg's own fontdb, not the document font collection — bundled/registered/`@font-face` fonts don't apply | blitz-paint / anyrender_svg, still in beta.4 | Avoid SVG text; overlay HTML text | Not reported |
| Bundled font family naming: fontique registers fonts under internal name (`"Inter Variable"`), so name-based defaults can silently bind to a system font or nothing | fontique | Register with `FontInfoOverride { family_name }` and wire generics by `FamilyId` | Working as designed; gotcha documented |
| A `box-shadow` whose colour is outside the sRGB gamut is painted with unclamped channels: blitz-paint converts shadow colours to sRGB without gamut mapping (`as_srgb_color`), and the blurred-rounded-rect paint behind every *blurred* shadow converts the raw floats to bytes with SIMD (vello_common `f32_to_u8`: float → u32, keep the low byte). Below 0 becomes 255 on AVX-512, wraps on AVX2, saturates on NEON/scalar; above 1 wraps dark everywhere. So `oklch(76.5% 0.177 163.2)` (Tailwind v4's emerald-400) glows red on x86, and output differs per CPU. Unblurred (offset/spread-only) shadows are solid fills since anyrender_vello_cpu 0.19, which saturate after premultiplying (so an above-1 channel on a translucent colour still comes out brighter than its clamped colour) | anyrender_vello_cpu 0.18–0.19 `draw_box_shadow` → vello_cpu 0.3–0.4 `fill_blurred_rounded_rect(_in)`; blitz-paint `color.rs`, still on blitz main @ `81b4896` | `EngineScene` (`src/scene.rs`) clamps `draw_box_shadow`'s colour per channel before premultiplication | Not reported (repro: `tests/test_box_shadow.py`; the blurred cases fail without the clamp on every CPU, the below-0 ones only on x86) |
| CSS `filter` is converted by blitz-paint but dropped unless anyrender_vello_cpu's `filters` feature is on (and never with `multithreading`, which turns it back off). vello_cpu implements flood/blur/drop-shadow/offset only; only a filter list's first node is converted | anyrender_vello_cpu 0.18–0.19 `push_layer` / `filters.rs`; vello_common 0.3–0.4 `filter/mod.rs` | `filters` feature on. 0.18 panicked (`unimplemented!()`) on the colour-matrix filters (`grayscale()`, `sepia()`, ...) and `EngineScene` dropped them; 0.19 drops them itself, so that guard is gone | 0.19 skips unsupported primitives (repro: `tests/test_filters.py`) |
| A non-isolated clip (`push_clip_path` / `push_clip_rect`) enclosing a vello_cpu filter layer is applied displaced down/right by the layer's filter padding (the blur's 3σ, snapped up to 4 device px). anyrender_vello_cpu 0.19 wraps every filter layer in such a clip, its filter region, so `filter: blur()`, a blurred `drop-shadow()` and a blurred `text-shadow` lost their halo above and left of the element; an `overflow: hidden` ancestor with square corners (a rect clip) cuts the filtered element itself on its top/left by up to that padding | vello_cpu 0.4 (also on vello main @ `84ffc24`); anyrender_vello_cpu 0.19 `push_layer` (also on anyrender main @ `92d2a9e`) | `EngineScene` clips the filter region with an isolated clip layer (which vello_cpu places correctly) and hands on the filter with an unbounded region. The enclosing-rect-clip case has no workaround (it would mean isolating every rectangular clip) | Not reported (repro: `src/scene.rs` tests; `tests/test_filters.py::test_blur_inside_a_rectangular_overflow_clip`, strict xfail) |
| `@font-face` sources with no `format()` hint and no URL file extension were silently skipped (data: URIs) | blitz-dom `fetch_font_face`, beta.1 | — | **Fixed** by beta.4 (format-less `data:font/ttf` URIs load) |
| CSS *animations* didn't apply to `<svg>` elements (static transforms did) | blitz-dom style/animation, beta.1 | — | **Fixed** by beta.4 |
| `DocumentMutator::set_style_property` didn't invalidate layout | blitz-dom 0.3.0-beta.1 | `Template.set_style` rewrites the `style` attribute instead (kept — equally correct, and no need to churn) | **Fixed** (#582) |
| System-font scan panicked when fontconfig is installed but zero fonts are (`font_sort(...).unwrap()` on `NoMatch`) — hit on fresh Home Assistant base images | fontique ≤ 0.11.1 `backend/fontconfig.rs` | Was: probe under `catch_unwind`. Dropped in 0.6.0; the `fontless-test` CI job remains as the regression test | **Fixed** in fontique 0.12 (`let Ok(..) else` skip) |
| `anyrender` failed to compile on 32-bit targets (`size_of::<FilterEffect>()` assertion assumed 64-bit pointers) | anyrender ≤ 0.13 | Was: no armv7 wheels | **Fixed** in anyrender 0.14 (per-pointer-width assertion) |

`text-shadow` is painted upstream since #984 (in our pin). `text-overflow: ellipsis` (open upstream as DioxusLabs/blitz#1015) is painted by the fork's `blitz-py` branch (adrienbrault/blitz#2), as is `outline-offset` (adrienbrault/blitz#1).

Also relevant but not engine bugs:

- **Where our Blitz comes from.** The fork [adrienbrault/blitz](https://github.com/adrienbrault/blitz) keeps `main` mirroring DioxusLabs/blitz `main`; each engine fix is a branch with a PR against the fork's `main`. The fork's `blitz-py` branch is upstream `main` plus the merged fix branches, and blitz-py pins one commit of it through `[patch.crates-io]` in `Cargo.toml` (and `fuzz/Cargo.toml`), keeping the crates.io version requirements (`=0.3.0-beta.4`, the version upstream's workspace still carries). Earlier releases: 0.5.0 pinned an upstream `main` commit as direct git dependencies; 0.6.0 used the crates.io `0.3.0-beta.4` release.
- **Bumping the pin.** On the fork, merge the new fix branches and/or upstream `main` into `blitz-py`. Here, set `rev` to the branch's new head in all `[patch.crates-io]` lines (`Cargo.toml` and `fuzz/Cargo.toml`), then: re-pair `anyrender` / `anyrender_vello_cpu` / `parley` / `fontique` / `peniko` with the `[workspace.dependencies]` of that commit's `Cargo.toml`; if its `[workspace.package] version` changed, move the four `blitz-*` requirements with it (otherwise cargo only warns "patch ... was not used" and builds the crates.io release); run `cargo update -p blitz-dom`, `cargo clippy --all-targets --locked -- -D warnings`, `cargo test --lib --locked`, build the wheel and run `pytest tests/`; re-check the findings above; commit `Cargo.lock` with it. CI builds with `--locked`, so a rev bumped without its lockfile fails. Past pairings: beta.1 needed `anyrender 0.11` + `anyrender_vello_cpu 0.14`; beta.4 `anyrender 0.14` + `anyrender_vello_cpu 0.18` + `parley 0.12`; upstream main @ `81b4896` `anyrender 0.15` + `anyrender_vello_cpu 0.19` + `parley`/`fontique 0.13`.
- Building from the sdist fetches the pinned commit from GitHub (cargo git dependency); the wheels need nothing.
- We build blitz-dom with `default-features = false` (dropping accessibility, file-input and custom-widget code), so every default feature we do want must be listed: `woff` (WOFF/WOFF2 `@font-face`) is enabled since 0.6.0 — before that, WOFF fonts silently fell back to the default face. `svg` arrives via blitz-paint.
- CSS floats are behind blitz-dom's opt-in `floats` feature (not in upstream's defaults either), which we do not enable: `float: left/right` boxes lay out as ordinary blocks.
- Parley 0.12 pixel-snaps line heights (`normal` for 16px Inter: 19.36 → 20px), shifting text by ≤1px vs 0.5.0 and changing `measure_text` heights accordingly.
- Upstream main applies `font-optical-sizing: auto` as an `opsz` variation (Blitz #1360): text in a font with an optical-size axis, like the bundled Inter Variable, uses the size's own cut, so large Inter text is narrower than with 0.6.0 (64px semibold "21.5°": 147 → 136px). `font-optical-sizing: none` restores the previous rendering.
